# JPCERT/CC注意喚起｜国内で相次ぐ不正アクセスの手口と不審なIPアドレス15件

2026年9月前後から、国内組織で不正アクセスによる個人情報等の漏えい被害が相次いでいます。JPCERT/CCは10月8日に注意喚起JPCERT-AT-2026-0030を公開し、翌9日の更新で不審な送信元IPアドレスを15件まで増やしました。あわせて国家サイバー統括室、経済産業省、金融庁、IPAも対策の徹底を呼びかけています。この記事では、2026年10月10日15時時点の一次情報をもとに、確認されている4つの攻撃手法、公表されたIPアドレスとUser-Agent、自社のログで確認したい点、遮断を検討するときの注意点を整理します。

## JPCERT-AT-2026-0030の概要

JPCERT-AT-2026-0030は、JPCERT/CCが2026年10月8日に公開した、直近の国内組織で相次ぐ不正アクセスに関する注意喚起です。特定の製品の脆弱性を扱う通常の注意喚起と異なり、複数の事案で見つかった攻撃手法と痕跡をまとめて示している点が特徴的です。基本情報は次の表のとおりです。

| 項目 | 内容 |
|---|---|
| 文書番号 | JPCERT-AT-2026-0030 |
| タイトル | 直近で相次いでいる国内組織における不正アクセスに関する注意喚起 |
| 公開日 | 2026年10月8日 |
| 最終更新日 | 2026年10月9日 |
| 10月9日の更新内容 | 概要と攻撃手法の章に追記（ケースA・Bへの送信元IPアドレスの追加、ケースDの新設） |
| 公表された痕跡 | 送信元IPアドレス15件、User-Agent 5件 |
| ドメイン・URL・ハッシュ値 | 公表なし |
| CVE番号が示された脆弱性 | CVE-2026-72898（Metabase）。ケースCのみで、ケースA・B・Dでは特定のCVEは示されていない |

注目したいのは、公開の翌日に内容が大きく増えた点です。初版で8件だった送信元IPアドレスは、10月9日の更新で15件になりました。JPCERT/CCは、新たな情報が判明した場合はページを更新するとしています。一度確認して終わりにせず、最終更新日と改訂履歴を定期的に見直す運用が欠かせません。更新の有無は改訂履歴で確認できます。

## 被害の状況と背景

今回の注意喚起の背景には、2026年9月前後から続く情報漏えい被害があります。ここでは、JPCERT/CCと国家サイバー統括室が公表している範囲で、どのようなシステムが被害に遭い、攻撃者が何をねらっているのかを確認します。

### 管理・運用側のシステムも被害に遭っている

JPCERT/CCによると、被害は複数の製品やサービスで発生しています。一般利用者向けのアプリだけでなく、BIツールや従業員向けの管理システムなど、不特定多数の利用を想定していない管理・運用側のシステムから内部の情報が漏えいした例もあります。一方で、技術情報の共有が不足しており、JPCERT/CCが把握している情報は限定的で断片的だとされています。注意喚起には、被害組織の名称や被害件数は書かれていません。

### 攻撃者のねらいは情報そのもの

国家サイバー統括室は10月9日の文書で、ウェブシステムの脆弱性の悪用、サプライチェーンを通じた侵害、データ管理の不備により、大量の個人情報を扱う事業者のシステムからデータが窃取される事案が複数確認されていると説明しています。攻撃者は情報そのものを標的にし、窃取した情報で脅迫したり不正に売買したりする傾向を強めているとのことです。JPCERT/CCも、ランサムウェア攻撃とは別の、大量の情報漏えいにつながる攻撃類型として今回の手法を取り上げています。

## 確認されている4つの攻撃手法

JPCERT/CCは、確認した攻撃をケースAからケースDの4つに分けて説明しています。共通する1つの脆弱性が使われているわけではなく、入口も手口も異なります。自社のシステムがどのケースに近いかを見ながら読み進めてください。

### ケースA：既知の脆弱性の探索と攻撃試行

1つ目は、標的ごとにさまざまなソフトウェアの既知の脆弱性の有無をスキャンし、悪用を試みる手法です。JPCERT/CCは、単一の共通した脆弱性が悪用されているわけではないと明記しています。設定ファイルやバックアップファイルの窃取など、機器の管理不備を突く攻撃の可能性にも触れています。対象製品は特定されておらず、2026年10月7日ごろに悪用された送信元IPアドレスが1件示されています。

### ケースB：API経由の不正操作

2つ目は、アプリの管理用APIへ不正なリクエストを送る手法です。入口として、公開されているスマートフォンアプリを解析してAPIのエンドポイントやキーを特定する、画面操作では実行できない内部APIを攻撃する、他システムの侵害で窃取したAPIキーを使う、の3つが挙げられています。内部APIへの攻撃では、ユーザー権限の変更、不正アカウントの作成、認証トークンの有無や形式を変えたときの応答の確認、NoSQLインジェクションによるアカウント情報の特定が行われ、情報の不正な書き換えなどが発生しました。

### ケースC：Metabaseの脆弱性CVE-2026-72898の悪用

3つ目は、BIツールMetabaseのSQLインジェクションの脆弱性CVE-2026-72898を悪用する手法で、APIへの不正なリクエストを通じて行われます。影響を受けるバージョンと対策は、2026年8月14日公開の注意喚起JPCERT-AT-2026-0023にまとめられています。悪用は8月上旬から9月上旬に確認されているため、該当するバージョンを使っている場合は、修正版の適用とあわせて当時のアクセスログも確認しましょう。

### ケースD：アプリケーションサーバーへのWebシェル設置

4つ目は、10月9日の更新で追加された手法です。公開Webサーバーからアクセスできるアプリケーションサーバー上にWARファイルが設置され、その中のJSPファイルが簡易的なWebシェルとして動作していました。このWebシェルは、特定のクエリパラメーターで受け取った値をシェルコマンドとして実行します。9月ごろに、GETとPOSTによる繰り返しのアクセスが確認されています。ファイル名、設置パス、ハッシュ値、対象製品は公表されていません。

## 公表された不審な送信元IPアドレスとUser-Agent

### User-Agentの例5件

User-Agentは、ケースBで3件、ケースCで2件が例として示されています。コマンドラインツールやスクリプトからのアクセスを示す文字列が中心で、ブラウザーを装った文字列も1件含まれます。IPアドレスが変わっても同じ文字列が使われることがあるため、送信元IPアドレスと組み合わせて検索すると見落としを減らせます。

ただし、curlやpython-requestsは、監視ツールやシステム間連携など正規の用途でも広く使われています。User-Agentは送信側で自由に書き換えられるため、一致しただけで攻撃とは判断できませんし、一致しないから安全とも言えません。あくまで、調査対象の通信を絞り込むための手がかりとして使いましょう。

## 企業が確認したいログと遮断時の注意点

公表された痕跡は、自社への攻撃の有無を調べる材料になります。ここでは、JPCERT/CCとIPAの記載をもとに、確認したいログ、遮断を検討するときの注意点、侵害が疑われる場合の動き方を順に説明します。

### 確認したいログと設定

まず、インターネットに公開しているWebサーバーやAPIのアクセスログを対象に、15件の送信元IPアドレスからの通信を探します。期間は、最も古い時期が示されているケースCにあわせて、2026年8月上旬から現在までを目安にするとよいでしょう。IPAは、直近1か月から始めて3か月へ段階的に広げる進め方を示しています。

- 公開しているWebサーバーやAPIのアクセスログに、15件のIPアドレスや5件のUser-Agentと一致する通信がないか
- APIのログに、ユーザー権限の変更、身に覚えのないアカウントの作成、不正な形式の認証トークンを付けたリクエストがないか
- Metabaseを使っている場合、パスワードリセット用APIへのPOSTが400で応答した直後に、ユーザー情報取得用APIへのGETが200で応答した記録がないか
- アプリケーションサーバーに見覚えのないWARファイルがないか、特定のJSPファイルへGETやPOSTが繰り返されていないか
- 利用中の外部サービスで、ログイン失敗の件数、ログイン元のIPアドレス、時間帯に異常がないか
- 作成した覚えのないアカウントや、無効化したはずなのに有効になっているアカウントがないか

確認の対象は、一般利用者向けのサービスだけではありません。JPCERT/CCは、従業員向けシステムやBIツールなど、不特定多数の利用を想定していないシステムにも同様の点検を勧めています。IPAも、クラウドサービスやVPNといった利用中の外部サービスを洗い出したうえで、認証まわりの記録を確認するよう求めています。

### 遮断を検討するときの注意点

公表されたIPアドレスを一律に遮断するかどうかは、慎重に判断してください。前述のとおり、JPCERT/CCは調査時点で正規利用されている可能性に触れており、VPNの出口やクラウドのIPアドレスは別の利用者に再び割り当てられることがあります。遮断する前に、過去の通信履歴から自社の業務や取引先の通信が含まれていないかを確認しましょう。遮断した場合も、過去に通信があったかどうかの調査は別に必要です。

### 侵害が疑われる場合の動き方

不審な通信や設定変更が見つかった場合について、IPAはインシデントと判定し、専門ベンダーによる詳細な調査を行うことを強く推奨しています。JPCERT/CCも、インシデント対応依頼や相談の窓口を案内しています。経済産業省は、所管業界の事業者に対し、被害やその可能性があるときは業所管の担当課室へ速やかに連絡するよう求め、警察への通報や相談も積極的に検討するよう促しています。証拠となるログは、上書きされる前に保全しておきましょう。

## 利用者が注意したいこと

サービスを利用する側も、情報が漏えいしている可能性を前提に備えておくと安心です。JPCERT/CCは事業者に対し、情報漏えいを想定して、多要素認証の設定など二次被害を防ぐための呼びかけを平時から準備するよう求めています。

利用者としては、同じパスワードを複数のサービスで使い回さない、多要素認証を有効にする、利用中のサービスを名乗るメールやSMSのリンクを安易に開かない、といった基本的な対策を見直しておきましょう。

## 再発を防ぐための対策

公表された痕跡の確認とあわせて、同じ手口を通さないための対策も進める必要があります。ここでは、JPCERT/CCが示すAPIの対策と、政府機関が10月9日に相次いで公表した対応要請の要点を整理します。

### APIと公開範囲の見直し

JPCERT/CCは、API経由のアクセスへの対策と、汎用的な対策の2つに分けて推奨事項を示しています。今回はアプリの解析や内部APIへの攻撃が確認されているため、画面から呼び出せないAPIは外部から見えないという前提を捨てることが出発点になります。注意喚起に挙げられている主な対策は次のとおりです。

- 単位時間あたりのリクエスト件数を制限し、ログイン、パスワードリセット、SMS送信、検索などの機能には個別の制限を設ける
- 非公開のAPIを含むすべてのエンドポイントでアクセス制御を行い、許可した利用者とHTTPメソッドだけを受け付ける
- 利用者とAPIトークンの権限を必要最小限にし、トークンには適切な有効期限を設定する
- 不要になったトークンや漏えいが疑われるトークンを、速やかに無効化できるようにする
- 業務上不要なサービスや管理機能のインターネット公開を停止し、利用地域が限られる場合はアクセス元の地域を制限する
- 既知の脆弱性の影響を受けるバージョンには修正版を適用する
- 保存期間を過ぎたデータや、利用目的を終えたデータを残さない

これらに加えて、JPCERT/CCは、Webサーバーが侵害されたあとの横展開への対策と、不正アクセスの検知体制や初動対応の見直しも挙げています。APIの対策の詳細については、OWASPのAPI Security Top 10とREST Security Cheat Sheetを参照するよう案内しています。開発を委託している場合は、委託先とも認識を合わせておきましょう。

## 今回の事案から得られる教訓

JPCERT/CCと政府機関による一連の公表からは、特定の製品に限らず、多くの組織に共通する課題が読み取れます。ここでは、公開範囲と保有データの把握、技術情報の共有という2つの観点から、今後の運用に生かしたい点をまとめます。

### 公開範囲と保有データを把握する

今回の被害では、BIツールや従業員向けの管理システムなど、社内向けのつもりで運用していたシステムが入口になった例があります。どのシステムがインターネットから到達できるのか、そこにどのデータが置かれているのかを把握していなければ、ログを調べる範囲も決められません。国家サイバー統括室とJPCERT/CCがそろって、保有する情報の棚卸しと不要なデータの削除を挙げているのは、漏えいしたときの被害を小さくするためです。

### 技術情報を早く共有する
