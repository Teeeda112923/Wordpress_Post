# Fireworks AIで情報漏えいが拡大｜請求情報・データセット・モデル重みに影響、利用者の対策

AI推論基盤を提供する[Fireworks AI](https://fireworks.ai/)は2026年11月9日、10月に公表した不正アクセスの調査結果を更新し、請求情報などに加えて、一部の顧客ではデータセットと未完成のモデル重みにも影響があったと明らかにしました。
支払いカード番号は保管しておらず、影響はありません。
10月23日に第三者のクラウド事業者で起きた事故が追加の侵入につながったとされ、調査は現在も続いています。
当初の発表から影響範囲が広がっているため、利用者は通知の有無を確認し、APIキーなどの認証情報の入れ替えを進めてください。

## この記事の要点

Fireworks AIが2026年11月9日に更新した公式のセキュリティ速報に基づき、押さえておきたい要点を5つにまとめました。
同社は現在も調査を続けているため、今後さらに新しい事実が判明する可能性があります。数字や影響の範囲は、利用の前に公式発表で必ず再確認してください。
公式の速報で確認できる事実を、時系列と影響範囲の順に並べています。

- 2026年10月6日に社内の認証情報が不正に使われているのを検知し、当初は評価ジョブなどで使うシークレットへのアクセスのみが確認されていました。
- 10月23日に研究開発用マシンをホストするクラウド事業者で事故が起き、翌24日に開発用マシンを経由して追加の顧客データに影響が出ました。
- 影響は、リソースのメタデータ、請求情報、一部顧客のデータセットと未完成のモデル重みです。
- カード番号は保管しておらず影響なしで、推論、Training SDK、Nexusへの影響は検知されていません。
- 金銭目的の攻撃者によるLLMjackingとみられており、通知を受けた利用者は認証情報の入れ替えが必要です。

影響を受けた顧客の数は、更新された速報でも明らかにされていません。
通知メールが届いている利用者は、その案内を最優先で確認してください。
通知を受けていない利用者の備えについては、後述の利用者向けの対策の章で整理しますので、あわせて参考にしてください。
また、Notion AIのように利用中のサービスを通じて間接的に影響を受ける場合もあるため、自社が使っているサービスからの案内にも、あわせて目を通してください。

## 何が起きたのか？発覚から更新公表までの時系列

事案は、10月6日の社内認証情報の不正使用の検知と、10月23日から24日にかけての第三者クラウド経由の侵入という、2段階で進みました。
ここでは公式の速報に沿って、いつ何が起きたのかを時系列で丁寧に確認します。

### 2段階で進んだ出来事の流れ

最初の発表は10月9日でしたが、その時点で確認されていたのは、評価ジョブなどで使うシークレットへのアクセスだけでした。
その後の調査で、アカウント情報や請求情報への影響が判明し、11月9日に更新されています。
時刻は米国太平洋時間で、日本時間とは16〜17時間ほどの差があります。主な出来事は次のとおりです。

| 日付（米国太平洋時間） | 出来事 |
|---|---|
| 10月6日 9時 | 社内認証情報の不正使用を検知し、封じ込めを開始 |
| 10月7日 7時 | 影響を受けた顧客への通知を開始 |
| 10月9日 | 16時に社員のAPIキーを入れ替え、18時に影響顧客への通知を完了、22時に速報を公開 |
| 10月10日 | 追加のユーザーAPIキーを失効し、サービスアカウントのトークンを入れ替え |
| 10月23日 | 研究開発用マシンをホストしていたクラウド事業者でセキュリティ事故が発生 |
| 10月24日 | 第三者が同クラウド環境経由で開発用マシンに到達し、不正なワークロードを実行。追加の顧客データに影響 |
| 10月25日 | 顧客が利用するプラットフォームへの不正アクセスの成功は確認されていない |
| 11月9日 | 速報を更新し、影響範囲の拡大を公表 |

10月24日の活動は同日中に検知され、即時の是正措置と既知の重大な脆弱性への対処が行われました。
一部の報道は、10月24日の侵入を2件目の攻撃として数えています。
一方で同社は、あくまで10月の事案の更新情報として説明しています。
数え方は報道によって異なりますが、被害の実態を見るうえでは、侵入が2回あったかどうかより、どのデータにいつ影響が及んだかを押さえることが重要です。

## 漏えいした情報は？影響を受けた3つのデータ

影響を受けたのは、リソースのメタデータ、請求情報、一部の顧客のモデル重みとデータセットの3分類です。
加えて、一部のアカウントではシークレットも対象でした。ここでは分類ごとの内容と、影響がないとされた範囲を順に確認します。

### 公式が示した3つのデータ分類

速報が示す3分類の内容は、次の表のとおりです。
モデル重みとは、AIが学習した結果を数値で保存したファイルのことで、企業が独自に調整したモデルは大きな資産になります。
今回対象になったのは完成したモデルではなく、未完成のものと説明されています。
なお、請求情報に含まれる住所や支払い履歴は、企業の取引関係の推測につながり得る情報でもあります。

| 分類 | 主な項目 |
|---|---|
| リソースメタデータ | リソース識別子、表示名、説明、作成日時 |
| 請求情報 | 請求先・配送先住所、請求書と支払い履歴、残高、クレジット利用状況 |
| モデル重みとデータセット | 一部の顧客に限り、未完成のモデル重みとデータセットの一部 |

最初の発表では、評価ジョブなどで使うシークレット（APIキーやトークン）が一部のアカウントで取得されていました。
シークレットは別のサービスに接続する鍵となるため、流出した場合は発行元での無効化が必要になります。
鍵が悪用されると、外部のクラウドやAIサービスにまで被害が広がるおそれがあるため、入れ替えは早めに行うことが大切です。

### 影響がないとされたもの

支払いカード番号は同社が保管していないため、影響はないとされています。
また、推論、Training SDK、Nexusについても影響は検知されていません。
これらは標準でゼロデータ保持、つまり入力した内容を保存しない設計とされています。

### Notionなど利用企業への波及

Notionは、Fireworksのインシデントの影響を受けたのは全ワークスペースの1%未満だと案内したと報じられています。
対象にはNotion AIとのチャット記録が含まれ、大半は個人や組織に紐づかない形だったとされています。
利用企業のサービスを通じて、間接的に影響を受ける場合がある点には注意が必要です。

## なぜ起きたのか？第三者クラウド経由の侵入とLLMjacking

攻撃の入口は、Fireworksの研究開発用マシンをホストしていた第三者のクラウド事業者でした。
同社は、金銭を目的とする攻撃者がLLMjackingに関与しているとみています。ここでは公表されている経路と、手口の背景を整理します。

### 公表されている侵入経路

10月23日にクラウド事業者で事故が起き、翌24日に攻撃者がそこから同社の開発用マシンへ到達しました。
クラウド事業者の名称は公表されていません。
10月6日の社内認証情報がどのように使われたのか、その入口についても、公表内容からは分かりません。

### LLMjackingとは

LLMjackingとは、盗んだAPIキーなどを使い、他人が契約しているAIモデルを無断で使う手口です。
Googleの脅威インテリジェンス部門とMandiantは11月2日、盗まれたAPIキーなどで得た利用権が、LLM Mixersと呼ばれる不正な中継サービスで転売されていると報告しました。
被害者には利用料金が請求され、1日で10万ドルを超えた事例もあるとされています。

### 攻撃者の狙いはモデル重みなのか

FireworksのCEOは、攻撃者の狙いはモデル重みの窃取ではないとの見方を示したと、英The Registerが報じています。
同記事によると、ダウンロードの大半は一部だけで途中で止まったとされます。
ただし、データが攻撃者の手元に渡った事実は変わらないため、影響を受けた顧客は慎重に対応する必要があります。

## Fireworks AIの対応は？実施した対策

同社は、認証情報の入れ替え、ネットワークの隔離、データ保護の強化、ログの強化に取り組んでいます。
フォレンジック調査では、Palo Alto Networks傘下の[Unit 42](https://unit42.paloaltonetworks.com/)の支援を受けています。ここでは具体的な対策と機能制限を見ていきます。

### 公表された4つの対策

速報に示された対策は、次の4つです。
法執行機関への通報も済ませており、調査は継続中とされています。
各項目は、再び同じ経路を使われないための土台となる取り組みで、認証情報、ネットワーク、データ、ログの4つの観点で整理されています。
なお、これらは事案への対応として同社が実施したと説明しているものであり、第三者による検証結果が公表されているわけではありません。

1. **アクセスと認証情報の封じ込め。** 認証情報とサービスアカウントの失効と再発行、不要な昇格権限の削除、新たな不正認証情報の作成を防ぐ統制の強化。
2. **ネットワークの隔離。** 不正なネットワーク経路の遮断と、影響を受けたシステムの隔離。
3. **データ保護。** データストレージと分析システムへのアクセスを見直し、公開や不正アクセスを防止。
4. **フォレンジックと監査の完全性。** ロギングと監視の強化。

これらの対策は、すでに起きた侵入への対処と、今後の再発防止の両方を狙ったものです。
同社は、新しい情報が判明すれば速報を更新するとしているため、利用者は定期的に公式ページを確認すると安心です。
調査の結果次第では、対策の追加や、影響範囲のさらなる修正が発表される可能性も残されています。
そのため、一度確認して終わりにせず、更新があったときに気づける体制を整えておくことが大切です。

### 一部機能の一時停止

調査期間中は、Batch Inferenceやデータセットを使うトレーニングで、利用者が自分で行うデータセットのアップロードとダウンロードが停止されています。
Training SDKは引き続き利用でき、Fireworks Labベースのトレーニングは隔離環境で運用されています。

## 利用者がすべき対策は？通知の有無で分かれる対応

対応は、同社から個別の通知が届いたかどうかで変わります。
影響を受けた顧客には、影響の詳細と推奨される対応が個別に通知されます。
まずは、登録しているメールアドレスの受信箱と迷惑メールフォルダで、通知メールの有無を確認してください。

### 通知を受けた利用者の4つの行動

10月9日の速報では、通知を受けた利用者に次の4つの行動が案内されていました。
どれも認証情報の悪用を防ぐための基本的な手順で、通知メールの内容と合わせて確認する必要があります。
特に、Fireworks上でシークレットを削除しただけでは、元の認証情報は無効にならない点に注意してください。実際に鍵を発行したプロバイダー側での操作が欠かせません。

1. **失効したAPIキーを作り直す。** 無効化されたキーは使えなくなるため、新しいキーを作成してアプリケーションを更新する。
2. **第三者の認証情報を発行元で入れ替える。** 通知で示された認証情報は、発行したプロバイダーで入れ替えるか失効させる。
3. **アクセスログを確認する。** 不審な活動が見つからなくても、入れ替えは実施する。
4. **見覚えのないリソースを探す。** APIキー、ユーザー、evaluator、学習ジョブ、データセットを確認し、該当があればFireworksへ連絡する。

この4つは順番に意味があります。
まず使えなくなった鍵を作り直して業務を戻し、次に連携先の鍵を入れ替え、そのうえでログと見覚えのないリソースを調べる流れが現実的です。
作業の記録を残しておくと、後から社内や取引先へ説明する際に役立ちます。
複数のシステムで同じ鍵を使い回している場合は、使い回している全ての箇所を洗い出して、同時に入れ替えることが重要です。入れ替えの途中で一部だけ古い鍵が残ると、そこが新たな弱点になります。

### 通知を受けていない利用者の備え

10月の速報では、通知を受けていない利用者に事案固有の対応は求められていません。
ただし調査は継続中で、影響範囲は一度広がっています。
念のため、Fireworksで使っているAPIキーの棚卸しと、請求画面での不審な利用の有無の確認をおすすめします。

## 組織が今できる予防策

AI基盤を利用する組織は、鍵の管理、預けるデータの範囲、利用状況の監視を見直すことで、同様の事故による被害を小さくできます。
ここでは、今回の件から導ける予防策を3つ挙げます。いずれも、AI基盤に限らず他のクラウドサービスにも応用できる考え方です。

### APIキーとシークレットを入れ替えやすくする

最も効くのは、鍵を定期的に、かつ迅速に入れ替えられる状態にしておくことです。
[API](https://www.cybernote.click/2026/10/16/what-is-api/)の鍵は、使っている場所が分散すると、事故のときに全部を洗い出せません。
鍵の用途、発行元、保管場所を台帳にまとめておくと、入れ替えまでの時間を大きく短縮できます。

### 外部のAI基盤に預けるデータを見直す

データセットやモデル重みを外部基盤に置く場合は、その基盤が侵害されても困らない範囲に絞ることが大切です。
個人情報や機密情報は、匿名化や加工をしてから渡す、保管期間を決める、といった運用を検討してください。

### LLMjackingを想定して利用状況を監視する

LLMjackingの被害は、請求額の急増という形で現れます。
モデルの利用量に予算アラートを設定し、普段使わないモデルやリージョンへのアクセスを検知できるようにしておくと、発見が早まります。
Googleのブログも、検知や対策の手順を公開しています。

## 企業・情シス担当者への示唆

今回の件が示すのは、最初の発表が最終的な被害範囲とは限らないという現実です。
同社は10月の初回発表で、顧客のモデルやデータセットへのアクセスは確認されていないと説明していましたが、後の調査で一部が対象と分かりました。

### 初回発表は更新される前提で運用する

委託先や外部サービスの事故では、初報の後に影響範囲が広がることがあります。
初報の時点で影響なしと読み取れても、更新情報の確認を担当者と頻度を決めて続けることが大切です。

### 委託先のさらに先まで把握する

今回の入口は、Fireworksがさらに利用していたクラウド事業者でした。
自社が使うサービスだけでなく、そのサービスが依存する事業者まで視野に入れる考え方は、[ソフトウェアサプライチェーン攻撃](https://www.cybernote.click/2026/10/26/iac-cicd-software-supply-chain-attack/)への備えと共通しています。

### AI基盤が攻撃の対象になっている

AIの基盤や鍵は、攻撃者にとって金銭に変えやすい標的になっています。
[AIがサイバー攻撃を自律化する時代](https://www.cybernote.click/2026/10/07/ai-autonomous-cyberattack-glm-5-3-2026/)の動向とあわせて、AI利用の統制を情報セキュリティ方針に含めておきましょう。

カード番号は影響なしで、推論、Training SDK、Nexusへの影響は検知されていません。
