# GitHub攻撃「wfx-loot」とは？6万超のリポジトリが標的、CI/CDの秘密情報を盗む手口と確認方法

2026年11月10日ごろから、盗まれたGitHubの認証情報を使い、6万を超えるリポジトリに不正なコードを送り込む攻撃キャンペーン「wfx-loot」が、複数のセキュリティ企業から報告されています。

狙いは、CI/CD（ソフトウェアを自動でテスト・配布する仕組み）に保管された秘密情報です。AWSやAzureなどのクラウドの認証情報まで盗まれる可能性があります。

本記事では、各社が公開した報告をもとに、攻撃の手口と被害の見方、自分のリポジトリが影響を受けたかの確認方法、今日からできる対策を、順を追って整理します。

## wfx-lootキャンペーンの概要

wfx-lootは、Aikido Securityが命名した攻撃キャンペーンです。攻撃者は、盗んだGitHubのトークン（利用者の代わりに操作するための鍵）を使って、書き込み権限のあるリポジトリへ次々にコードを送り込みます。ソフトウェアの欠陥を突くのではなく、正規の権限を悪用する点が特徴です。確認されている要点を、次の表にまとめました。

| 項目 | 内容 |
| --- | --- |
| 報告時期 | 2026年11月12日〜13日（各社のブログ公開日） |
| 報告した企業 | Aikido Security、GitGuardian、Chainguard、SafeDep、StepSecurity |
| 攻撃の開始 | 11月10日12:45 UTC（日本時間21:45）ごろから本格化 |
| 使われた手段 | 盗まれたGitHubの認証情報による書き込み |
| 主な狙い | CI/CDの秘密情報、クラウドの認証情報、AIサービスのキー |
| GitHubの公式コメント | 確認した報告には記載なし |

数値は各社で異なります。Aikidoは約4,837アカウントが61,764リポジトリを狙ったと報告しました。一方、GitGuardianは自社データで2,367アカウント、17,715リポジトリを確認しています。集計の方法と範囲が違うためで、どちらかが誤りというわけではありません。この記事では、数字は出典の企業名を添えて書きます。

### 脆弱性ではなく「盗まれた権限」の悪用

セキュリティ企業のStepSecurityは、攻撃者はGitHub Actionsの不具合を悪用しているわけではないとの見方を示しています。有効なトークンを使って、正規の操作として書き込んでいるためです。

そのため、特定のソフトウェアを更新すれば防げる、という種類の問題ではありません。トークンの管理と、書き込み権限の見直しが対策の中心になります。

## 攻撃の流れ

報告によると、攻撃は段階的に進みます。まず書き込み権限があるかを確かめ、あれば不正コードを送り込み、跡を消します。Aikido、Chainguard、GitGuardianの3社の報告で共通している流れを、順に説明します。

### 1. 試しにプルリクエストを出す

最初に、`wfx-docs`というブランチから「docs: dependency audit notes」というタイトルのプルリクエスト（変更の提案）を出します。書き込み権限があるかを確かめる「探り」とみられます。

GitGuardianによると、このときは`docs/wfx-audit.md`というファイルが追加されます。探りの時点で、そのアカウントは侵害されたものとして扱うべきだとAikidoは指摘しています。

### 2. 不正コードを送り込む

書き込めると分かると、攻撃者は不正コードを送り込みます。報告されている方法は主に3つあり、リポジトリの構成や設定に応じて使い分けられているようです。どの方法でも、通常の開発作業に見せかけたコミット名が付けられているため、履歴を流し読みしただけでは見落としやすくなります。主な3つの方法は、次のとおりです。

1. 既存のワークフロー（CI/CDの手順書）に、約1,500行の処理を追加する。コミット名は「ci: refresh build cache」
2. `.ci-`で始まるシェルスクリプトを置き、`package.json`のpostinstall（インストール直後に動く処理）から呼び出す。コミット名は「chore: add ci helper」
3. `chore/`で始まる使い捨てのブランチに、`build-audit-`で始まる名前のワークフローを置く。コミット名は「chore: add dependency audit workflow」

GitGuardianは、これらに加えて、既存のビルド用スクリプトの先頭や、デプロイ用のシェルスクリプトに処理を書き足す形も確認しています。つまり、新しいファイルが増えていないからといって、安全とは言い切れません。既存ファイルの変更履歴も、あわせて確認してください。身に覚えのない変更が見つかったら、コミットを書いた人とアカウントを必ず確認しましょう。

### 3. 跡を消す

Chainguardによると、攻撃者は約1分以内に変更を元に戻し、ワークフローの実行履歴とログも削除します。

このため、リポジトリを見ただけでは侵害に気づきにくくなります。実行履歴の削除が多く、被害は実際より小さく見えている可能性があるとAikidoは述べています。

## 何を盗まれるのか

不正コードが実行されると、CI/CDの実行環境にある秘密情報が外部へ送られます。リポジトリに保存した秘密情報だけでなく、実行環境が一時的に持っている認証情報も対象です。各社の報告から、盗まれるとされているものを分類しました。

### CI/CDの秘密情報

GitHub Actionsのsecrets（秘密情報）とvariables（変数）、GITHUB_TOKEN、OIDCトークン（クラウドへ安全にログインするための一時的な証明書）が狙われます。

実行環境のメモリを読み取り、画面に出ないよう隠された値を取り出す処理も報告されています。

### クラウドとAIサービスの認証情報

AWS、Azure、Google Cloud、Docker、Kubernetes、npm、PyPI、SSHなどの認証ファイルが対象です。OpenAIやAnthropicなど、AIサービスのAPIキーも含まれるとされています。

GitGuardianは、約90種類のAIサービス用キーの接頭辞を探す処理を確認しました。

### クラウドでの足がかりづくり

盗んだ情報を使い、AWSでは権限を引き受けて新しいアクセスキーを作ったり、信頼ポリシーを書き換えたりする動きが報告されています。

Azureでも、攻撃者が後から入れるように認証設定を追加する動きが確認されています。盗まれた情報を更新するだけでなく、クラウド側に残された足がかりまで消す必要があります。

## 被害の見方：数字が食い違う理由

報道や各社のブログには「4,800」「6万」「8,000」など、さまざまな数字が並んでいます。これは集計の対象や範囲が企業ごとに違うためで、どれかが間違いというわけではありません。数字は、何を数えたものかを区別して読むことが大切です。主な数字を、次の表に整理しました。数字の意味を取り違えないよう、数えた対象も添えています。

| 数字 | 何を数えたか | 報告元 |
| --- | --- | --- |
| 約4,837 | 探りのPRを出した侵害アカウント | Aikido |
| 61,764 | 探りの対象になったリポジトリ | Aikido |
| 1,800超 | 不正コードの実行が確認されたリポジトリ | Chainguard、Aikido |
| 8,093 | 悪意あるコミットを受けた公開リポジトリ | SafeDep |
| 2,367 | 自社データで確認したアカウント | GitGuardian |

表を読むときの大切な点は、狙われた数と、実際に不正コードが実行された数は別だということです。探りのPRが届いただけでは、秘密情報が盗まれたとは限りません。ただし、探りを出せたアカウントは書き込み権限を奪われている状態です。その点はAikidoも指摘しています。数字の大きさに驚くよりも、自分のアカウントが対象かどうかを確認することが先決です。SafeDepの8,093件も、実行の成功を意味するものではないとSecurityWeekは伝えています。

また、GitGuardianによると、ワークフローファイルを追加するタイプは、GitHubの仕組みで実行が保留（action_required）された例が見られました。一方、npmのインストール時に動くタイプはワークフローの変更を伴わないため、この保留の対象になりません。

### 公式情報で確認できていないこと

トークンがどこから盗まれたのかは、確認した報告には記載がありません。StepSecurityは、一部のPRをFly.ioのGitHub Appに発行されたトークンまで追跡しましたが、同社の基盤が侵害された証拠はないとしています。

GitHubの公式コメントも、確認した報告には見当たりません。プライベートリポジトリへの影響や、攻撃者が実際に情報を回収できた範囲も、現時点では分かっていません。

## 自分のリポジトリが影響を受けたか確認する方法

確認は、GitHub上の痕跡とクラウド側の痕跡の2か所で行います。痕跡は攻撃者が消している可能性があるため、「見つからない」ことは安全の証明になりません。Chainguardも、成果物やキャッシュがないことは未侵害の証拠にならないと注記しています。

### GitHub側で見るポイント

GitHub側では、攻撃者が残した変更の痕跡を探します。個々のリポジトリだけでなく、組織全体の履歴や、自分が共同作業者になっているリポジトリも対象です。報告で共通して挙げられている痕跡を、次にまとめました。1つでも見つかれば、侵害されたものとして扱ってください。なお、攻撃者は変更を元に戻して履歴を消すため、現在のブランチ一覧に何も残っていなくても、安心はできません。

- `wfx-docs`、`chore/`で始まる8文字のブランチ、`ci-check-`で始まるブランチ
- 「docs: dependency audit notes」というタイトルのプルリクエスト
- 「ci: refresh build cache」「chore: add ci helper」「chore: add dependency audit workflow」というコミット
- `.ci-`で始まるシェルスクリプト、`build-audit-`で始まるワークフローファイル
- ワークフローの実行番号の欠番（実行履歴が削除された可能性）

GitGuardianは、実行番号の欠番を「実行が作られた」ことの手がかりとして挙げています。履歴が削除されていても、番号の飛びは残るためです。あわせて、組織の監査ログで、ワークフローの承認や実行の記録も確認しましょう。自分の操作ではない承認や実行が残っていれば、すぐに管理者へ共有してください。確認は、早めに済ませておくと安心です。

### クラウド側で見るポイント

11月10日以降に、身に覚えのないアクセスキー、権限の変更、新しい認証設定が追加されていないかを確認します。

AWSでは、信頼ポリシーに全員を許可する記述がないか、セッション名が`wfx-`で始まるものがないかが目安です。Azureでは`wfx-ci-`で始まる名前の認証設定を探します。

## 今すぐできる対策

侵害が疑われる場合も、そうでない場合も、基本は同じです。盗まれた可能性のある鍵を無効にし、新しいものに取り替えます。順番を間違えると、更新した直後に再び盗まれるおそれがあるため、攻撃者が書き込める状態を先に止めることが大切です。

### 侵害が疑われるときの対応

不正なブランチやワークフローが見つかった、または実行の痕跡がある場合は、そのリポジトリのワークフローが到達できるすべての秘密情報が盗まれたものとして対応します。攻撃者がまだ書き込める状態では、更新した鍵もすぐに盗まれるおそれがあります。次の順に進めてください。なお、作業中に新しい不審な変更が見つかった場合は、手順を中断せず、記録を残しながら進めると、後の調査に役立ちます。

- 漏えいしたトークン、GitHub CLIのトークン、SSH鍵を失効する
- 組織とリポジトリのsecretsとvariablesをすべて更新する
- 不正なブランチ、ワークフロー、スクリプト、postinstallの記述を削除する
- クラウド側に追加された権限や認証設定を削除し、信頼ポリシーを元に戻す
- 必須チェックを再実行し、偽の成功表示が残っていないか確認する

AikidoとGitGuardianは、ワークフローで参照されていないと思われる秘密情報も含めて、すべて更新するよう勧めています。実行環境からは、参照していない値も読み取られる可能性があるためです。作業が終わるまで、該当リポジトリへの書き込みは控えてください。復旧の手順は、チームの責任者と共有しながら進めましょう。また、組織のセキュリティ担当者や、利用している外部サービスの管理者にも、必要に応じて状況を伝えてください。

### 今のうちにできる備え

被害を受けていなくても、同じ手口を前提に、書き込み権限と鍵の持ち方を見直しておくと安心です。今回の攻撃は、有効なトークン1つから広がっています。トークンが盗まれても被害を小さくできるよう、権限を絞り込み、不要な鍵を減らしておきましょう。見直しの例は、次のとおりです。すべてを一度に行う必要はないため、できるものから進めてください。

- 個人のトークンは、必要な範囲と期限を絞ったものを使う
- 使っていないトークン、OAuthアプリ、GitHub Appの権限を整理する
- 重要なブランチは保護し、ボットアカウントがその保護を回避できないか確認する
- ワークフローに渡す権限は、必要最小限にする
- 不審なPRやブランチの通知を、チームで見逃さない体制にする

なお、Chainguardは、アクションのバージョン固定やPRのレビューだけでは、最初の書き込みを防げなかったと述べています。鍵の管理と権限の絞り込みが優先です。まずは、今使っているトークンの一覧を確認するところから始めてみてください。npmを使う開発者は、ビルド時に`--ignore-scripts`を付けて、インストール時の処理を動かさない方法もあります。

## 日本の開発チームへの影響

GitHubは、日本の企業や自治体、個人開発者にも広く使われています。今回の報告は海外のセキュリティ企業によるものですが、日本の利用者が対象から除外されるという情報は、確認した報告には見当たりません。日本の開発チームも、自分のこととして確認しておく必要があります。

攻撃はアカウントの権限を足がかりにするため、リポジトリの公開・非公開や、組織の規模を問いません。特に、外部の委託先や協力会社が書き込み権限を持つ開発体制では、相手のアカウントが盗まれた場合も影響を受けます。

ソフトウェアの配布元が悪用される被害は、[Rank Math SEO Proのサプライチェーン攻撃](https://www.cybernote.click/2026/10/21/rank-math-seo-pro-cve-2026-111862-supply-chain-malware/)でも起きています。開発者を狙う攻撃の背景は、[サプライチェーン攻撃とは？npm汚染のCrowdSec事例と対策](https://www.cybernote.click/2026/09/24/supply-chain-attack-npm-crowdsec/)や、[北朝鮮のフェイススティーラーとは？](https://www.cybernote.click/2026/11/14/facestealer-north-korea/)も参考になります。

## まとめ

wfx-lootは、盗まれたGitHubの認証情報を使い、6万超のリポジトリに不正コードを送り込んでCI/CDの秘密情報を盗む攻撃です。ソフトウェアの脆弱性ではなく、正規の権限が悪用されています。

身に覚えのないブランチ、コミット、ワークフローの有無を確認し、疑わしければ鍵の失効と更新、クラウド側の確認を急いでください。数字は各社で異なり、トークンの入手経路やGitHubの公式見解も、確認した報告には見当たりません。続報が出たときは、本記事の内容と照らして、対応を見直してください。身近な開発チームにも、この情報を共有しておきましょう。
