# IaC・CI/CDを狙うソフトウェアサプライチェーン攻撃の手口と対策｜Terraformの事例

ソフトウェアサプライチェーン攻撃は、利用者が信頼している部品や開発工程に入り込み、そこから被害を広げる攻撃です。これまではライブラリの改ざんや、アップデートの悪用が主な手口でした。

近年は、インフラをコードで管理するIaCや、ビルドを自動化するCI/CDも攻撃の入口になりつつあります。2026年10月には、AWS SAM CLIのTerraform連携機能でOSコマンドインジェクションの脆弱性が公表されました。

本記事では、IaC・CI/CDが狙われる理由と主な手口、今すぐできる対策を、公的機関の資料をもとに解説します。

## ソフトウェアサプライチェーン攻撃の基本

IaCやCI/CDの話に入る前に、ソフトウェアサプライチェーン攻撃の定義と、近年注目が高まっている理由を簡単に整理します。攻撃の全体像や種類、国内外の被害事例を詳しく知りたい方は、関連記事もあわせてご覧ください。

### 攻撃者が信頼関係を悪用する攻撃

ソフトウェアサプライチェーン攻撃とは、ソフトウェアの開発や配布の過程に、不正なコードを紛れ込ませる攻撃です。攻撃者は標的を直接狙わず、標的が信頼して使う部品やツールを先に侵害します。

利用者は正規の入手先から受け取ったつもりでも、中身はすでに改ざんされています。一度の侵入で多くの組織に被害が広がる点が、この攻撃の大きな特徴です。

サプライチェーン攻撃の仕組みや3つの種類、代表的な被害事例は、[サプライチェーン攻撃とは？仕組みや被害事例、企業が取るべき対策と今後のトレンドを徹底解説！](https://www.cybernote.click/2026/07/02/%e3%82%b5%e3%83%97%e3%83%a9%e3%82%a4%e3%83%81%e3%82%a7%e3%83%bc%e3%83%b3%e6%94%bb%e6%92%83%e3%81%a8%e3%81%af%ef%bc%9f%e4%bb%95%e7%b5%84%e3%81%bf%e3%82%84%e8%a2%ab%e5%ae%b3%e4%ba%8b%e4%be%8b%e3%80%81/)で詳しく紹介しています。本記事では、そのうちIaCとCI/CDを入口とするものに絞って解説します。

### なぜサプライチェーン攻撃は増えているのか

[IPA（情報処理推進機構）](https://www.ipa.go.jp/)が2026年1月に発表した「情報セキュリティ10大脅威 2026」では、サプライチェーンや委託先を狙った攻撃が組織編の2位に入りました。前年に続く2位で、2019年の初選出から8年連続のランクインです。

背景には、開発でオープンソースや外部サービスへの依存が深まったことがあります。自社のコードを堅く守っていても、依存する部品が1つ侵害されれば被害は防げません。攻撃者にとって、少ない労力で多くの標的に届く効率のよい手段になっています。

## IaC・CI/CDとは何か

IaCとCI/CDは、クラウド時代の開発を支える基盤技術です。どちらも作業を自動化して効率を高める一方で、攻撃者にとっては魅力的な侵入口にもなります。ここでは、セキュリティの話に入る前提として、それぞれの仕組みと役割を簡単に確認します。

### IaC（Terraform）とは

IaC（Infrastructure as Code）とは、サーバーやネットワークなどのインフラ構成をコードで記述し、自動で構築する手法です。手作業による設定ミスを減らし、同じ環境を何度でも再現できる点が利点です。

代表的なツールが、[HashiCorp](https://www.hashicorp.com/)社のTerraformです。設定ファイルに構成を書き、実行計画（プランファイル）を確認してから適用する流れで使います。部品にあたるモジュールは、公開レジストリから外部のものを取り込んで再利用できます。

### CI/CDパイプラインとは

CI/CDとは、コードの変更を自動でテストし（CI：継続的インテグレーション）、本番環境まで自動で届ける（CD：継続的デリバリー）仕組みです。この一連の処理の流れを、パイプラインと呼びます。

[GitHub](https://github.com/)のGitHub ActionsなどのCI/CDサービスでは、ビルドやデプロイの手順を設定ファイルに書いておくと、変更のたびに自動で実行されます。IaCと組み合わせれば、インフラの変更もコードの変更と同じように自動で反映できます。

## IaC・CI/CDが狙われる背景と被害

IaCとCI/CDが狙われる最大の理由は、ビルド環境に重要な権限と秘密情報が集まることです。ここでは、その構造と、侵害されたときに想定される2つの被害を整理します。被害は自社だけでなく、顧客や取引先にまで及ぶ点に注意が必要です。

### ビルド環境に秘密情報が集まる構造

CI/CDでインフラを自動構築するには、クラウドを操作する権限が欠かせません。そのため、ビルド環境にはクラウドのアクセスキーやデプロイ用のトークン、署名鍵などが集まります。

さらに、IaCの設定ファイルやプランファイルはビルド時に自動で読み込まれます。これらを書き換えられれば、攻撃者は人の目を通さずに、ビルド環境で命令を実行できる可能性があります。

### 認証情報が盗まれる

ビルド環境で不正なコマンドが実行されると、そこにある認証情報が外部へ送られるおそれがあります。盗まれたアクセスキーが使われれば、本番のクラウド環境まで乗っ取られかねません。

こうした認証情報は、正規の権限として扱われる点が厄介です。攻撃者の操作が通常の運用と見分けにくく、発見が遅れる原因になります。

### ビルド成果物が改ざんされる

もう1つの被害は、ビルドの成果物そのものの改ざんです。攻撃者がビルド工程に手を加えれば、正規の手順で作られたように見えるプログラムに不正なコードを仕込めます。

改ざんされた成果物は、自社のサービスだけでなく、顧客や取引先にも配布されます。自社が被害者であると同時に、攻撃を広げる側に回ってしまう危険があります。

## IaC・CI/CDを狙う主な攻撃手口

IaC・CI/CDを入口とする攻撃には、いくつかの典型的な手口があります。ここでは代表的な4つの手口を、2026年10月に公表されたAWS SAM CLIの脆弱性など、実際の事例とあわせて取り上げます。最後に、攻撃経路と対策を一覧表で整理します。

### 悪意ある外部モジュールを紛れ込ませる

Terraformでは、公開レジストリやGitHub上のモジュールを取り込んで使うことがよくあります。攻撃者は、便利そうなモジュールを公開したり、既存モジュールの管理者アカウントを乗っ取ったりして、不正な処理を仕込みます。

利用者がバージョンを固定していないと、改ざん後の版が次のビルドで自動的に取り込まれてしまいます。人気のあるモジュールほど、影響を受ける組織の数も大きくなります。

### プルリクエスト経由で設定を混入させる

オープンソースや社内の共有リポジトリでは、外部の人がプルリクエストで変更を提案できます。CI/CDの設定によっては、レビュー前の変更でもビルドが自動で走ります。

攻撃者はこの仕組みを悪用し、設定ファイルに不正な記述を紛れ込ませたプルリクエストを送ります。ビルドが動いた時点で、攻撃者のコードがビルド環境の権限で実行されてしまいます。

### 開発ツールの脆弱性を突く

IaCやCI/CDで使う開発ツール自体に脆弱性があれば、正しく使っていても攻撃の入口になります。ツールは設定ファイルを読み込んで処理するため、ファイルの中身を悪用されると被害につながりやすいのです。

この種の脆弱性は、ツールを最新版に更新するまで残り続けます。開発者の端末やビルドサーバーに古い版が放置されていないか、定期的な確認が欠かせません。

### 事例：AWS SAM CLIのTerraform連携の脆弱性

[AWS](https://aws.amazon.com/jp/)は2026年10月22日（米国太平洋時間）、サーバーレス開発ツールAWS SAM CLIの脆弱性CVE-2026-115414を公表しました。Terraform連携機能（sam build --hook-name terraform）に、OSコマンドインジェクションの問題がありました。

この機能は、Terraformのリソースアドレスをシェルの命令に埋め込む際、一部の特殊文字しか無害化していませんでした。影響を受けるのはバージョン1.63.0〜1.166.1で、CVSS v3.1の基本値は7.8（High）です。

### SAM CLIの事例から分かること

AWSの説明によると、Terraformの設定やプランファイルを操作できる攻撃者は、ビルドを実行するホスト上で任意のコマンドを実行できます。命令はビルド中に動き、AWSの認証情報がなくても、ビルドが失敗しても実行されます。

その結果、ビルド環境にあるCI/CDの秘密情報が盗まれたり、成果物が改ざんされたりするおそれがあります。設定ファイルが攻撃経路になるという、IaC特有のリスクを示す事例です。

### CI/CDの部品を乗っ取る（tj-actionsの事例）

2025年3月には、GitHub Actionsで人気の部品tj-actions/changed-filesが侵害されました。[CISA（米国サイバーセキュリティ・社会基盤安全保障庁）](https://www.cisa.gov/)は、アクセスキーやGitHubのトークン、npmのトークン、秘密鍵などが漏えいするおそれがあると警告しています。

CISAはこの問題（CVE-2025-30066）を、悪用が確認された脆弱性のカタログ（KEV）に追加しました。CI/CDの部品1つが侵害されるだけで、利用するリポジトリの秘密情報が危険にさらされることを示した事例です。

### 攻撃経路と対策の早見表

ここまで紹介した手口は、入口こそ違うものの、ビルド環境で攻撃者のコードを動かすという点で共通しています。そのため、対策も入口ごとに個別に考えるより、全体を見渡して優先順位をつけることが大切です。下の表は、主な攻撃経路ごとに具体例と有効な対策を整理したものです。自社の環境に当てはまる行がないか、確認してみてください。

| 攻撃経路 | 具体例 | 主な対策 |
|---|---|---|
| 外部モジュール | 改ざんされたTerraformモジュール | バージョンの固定、入手元の確認 |
| プルリクエスト | 設定ファイルへの不正な記述 | 外部からの変更は承認後にビルド |
| 開発ツール | AWS SAM CLIの脆弱性 | ツールの定期更新、版の棚卸し |
| CI/CDの部品 | tj-actions/changed-filesの侵害 | コミット単位での固定、権限の最小化 |

表を見ると分かるとおり、多くの対策は特別な製品を導入しなくても始められます。バージョンの固定や権限の見直しは、設定を変えるだけで効果が出るものも少なくありません。まずは表の中から、自社ですぐに着手できる項目を1つ選んで実行することをおすすめします。具体的な進め方は、後ほど対策の章で詳しく解説します。

## ベンダー・公的機関の対応

ソフトウェアサプライチェーン攻撃に対しては、ツールを提供するベンダーと公的機関の双方が対応を進めています。ここでは、AWS、CISA、経済産業省の取り組みを紹介します。各機関の発表内容は、自社の対策を考える際の参考資料としても活用できます。

### AWSの対応

AWSはSAM CLIの脆弱性について、修正版1.166.2を公開しました。最新版への更新に加え、フォークや派生したコードを使っている場合は修正を取り込むよう呼びかけています。

すぐに更新できない場合の回避策として、ビルドに渡すTerraformの設定とプランファイルを、信頼できる入手元のものに限ることを挙げています。外部のモジュールや共有リポジトリを監査することも推奨されています。

### CISAの対応

CISAは、tj-actions/changed-filesの侵害を受けて注意喚起を出し、修正版v46.0.1への対応を促しました。あわせて、サードパーティ製のGitHub Actionsを使う際のセキュリティを強化するよう求めています。

KEVカタログへの追加は、米国の連邦政府機関に対応を義務づけるものです。民間企業にとっても、優先して対処すべき問題を見極める目安として役立ちます。

### 経済産業省のSBOM導入の手引

[経済産業省](https://www.meti.go.jp/)は、「ソフトウェア管理に向けたSBOM（Software Bill of Materials）の導入に関する手引」を公開しています。SBOMとは、ソフトウェアに含まれる部品の一覧表のことです。

手引では、企業がSBOMを導入し、脆弱性の管理などに役立てるための手順や考え方が示されています。どの部品を使っているかを把握することは、サプライチェーン攻撃への備えの土台になります。

## 利用者が注意すべきポイント

IaC・CI/CDを使う開発者や運用担当者には、日々の運用の中で気をつけるべき点があります。攻撃の多くは、自動化の便利さに慣れて確認を省いたところを突いてきます。ここでは、見落としやすい2つのポイントを取り上げます。

### 外部からの変更をそのままビルドしない

外部の人が送ったプルリクエストや、共有リポジトリから取り込んだ設定ファイルは、内容を確認する前にビルドしないことが基本です。CI/CDの設定で、承認された変更だけがビルドされるようにしておきましょう。

特に、本番環境の秘密情報にアクセスできるジョブは、外部からの変更で起動しないよう分けておく必要があります。テスト用と本番用で、使える権限を分けておくと安全です。

### ビルドの成否だけで安全と判断しない

ビルドが失敗したから大丈夫、と考えるのは危険です。SAM CLIの事例のように、不正な命令はビルドの途中で実行され、結果が失敗でも被害は起きています。

不審なビルドの失敗が続いたときは、ログを確認し、想定外の通信やコマンドがないかを調べましょう。必要に応じて、ビルド環境の秘密情報を入れ替える判断も求められます。

## IaC・CI/CDのサプライチェーン攻撃への対策

IaC・CI/CDを狙う攻撃への対策は、ツール、部品、権限、可視化の4つの観点で考えると整理しやすくなります。ここでは、それぞれの具体的な進め方を解説します。いずれも大きな費用をかけずに始められるものを中心に紹介します。

### 開発ツールを最新に保つ

SAM CLIのような開発ツールは、開発者の端末やビルドサーバーに個別に入っていることが多く、更新が漏れやすい傾向があります。どこにどの版が入っているかを把握し、定期的に更新する運用を作りましょう。

ビルドに使うコンテナイメージにツールを含めている場合は、イメージの作り直しも必要です。脆弱性情報を定期的に確認し、該当する版を使っていないかをチェックします。

### モジュールとCI/CDの部品の版を固定する

Terraformのモジュールは、バージョンを指定して取り込めます。プロバイダーについても、依存関係のロックファイル（.terraform.lock.hcl）で版を固定できます。

GitHub Actionsの部品は、タグではなくコミットのハッシュ値で指定する方法が推奨されています。タグは後から付け替えられるため、改ざんされた版が紛れ込むおそれがあるからです。

### ビルド環境の秘密情報を最小化する

ビルド環境に置く秘密情報は、必要なものだけに絞ります。長期間使えるアクセスキーを置くのではなく、OIDCなどを使ってビルドのたびに短時間だけ有効な認証情報を発行する方式が有効です。

権限も、そのジョブに必要な範囲に限定しましょう。万一盗まれても、使える期間と範囲が限られていれば被害を小さく抑えられます。

### 静的解析とSBOMで見える化する

対策の最後は、自社の環境で何が使われているかを見える化することです。IaCの設定ファイルは、専用の静的解析ツールで危険な設定がないかを自動でチェックできます。また、SBOMで使っている部品の一覧を管理しておけば、新しい脆弱性が公表されたときに影響の有無をすぐ判断できます。日々の運用では、次の項目を定期的に確認するとよいでしょう。

- 開発ツールとビルド用イメージのバージョン
- Terraformのモジュールとプロバイダーの固定状況
- GitHub Actionsなど外部部品の指定方法（コミット単位か）
- ビルド環境に置いている秘密情報の種類と有効期限
- 外部からの変更でビルドが起動する設定になっていないか

これらの確認項目は、一度にすべて対応する必要はありません。影響の大きい本番環境に関わるパイプラインから順に点検し、少しずつ範囲を広げていくのが現実的です。確認結果を記録しておけば、次回の点検や監査の際にも役立ちます。担当者を決め、四半期に1回など定期的に見直す仕組みを作ることが、継続的な対策につながります。

## 業界への教訓：設定ファイルもサプライチェーンの一部

これまでサプライチェーンの対策というと、ライブラリや委託先の管理が中心でした。しかしIaCやCI/CDの普及により、インフラの設定ファイルやビルドの手順そのものが守るべき対象になっています。

SAM CLIやtj-actionsの事例は、開発を効率化する仕組みが、そのまま攻撃者の近道にもなりうることを示しました。コードと同じように、設定ファイルやビルド環境もレビューと管理の対象に含める視点が求められています。

## まとめ

ソフトウェアサプライチェーン攻撃は、利用者が信頼する部品や開発工程を悪用する攻撃です。IPAの10大脅威でも2位に入るなど、組織にとって重要な脅威であり続けています。

近年は、IaCやCI/CDのビルド環境が新たな入口になっています。AWS SAM CLIの脆弱性やtj-actionsの侵害は、設定ファイルや外部の部品を通じて秘密情報が狙われる現実を示しました。

対策の基本は、ツールの更新、版の固定、秘密情報の最小化、見える化の4つです。まずは本番環境に関わるパイプラインから、できるところで点検を始めましょう。
