# eMudhraの中間CA証明書8枚で秘密鍵が漏えい　鍵生成のミスで誰でも復元可能な状態に

インドの認証局eMudhra（イーマドラ）で、中間CA証明書8枚の秘密鍵が誰でも復元できる状態だったことが、2026年10月17日に判明しました。悪用されれば、あらゆるWebサイトになりすます偽の証明書を発行できる重大な問題です。

主要ブラウザはすでに該当する証明書をブロックしています。しかし、ブラウザ以外のアプリやサーバー、ネットワーク機器では、証明書ストアを含むソフトウェアの更新が必要なケースが残っています。

本記事では、何が起きたのか、秘密鍵が漏えいした原因と各社の対応、利用者と企業がとるべき対策を順に解説します。

## eMudhra中間CA証明書の秘密鍵漏えいの概要

今回の問題は、外部からの侵入による盗難ではなく、認証局自身の鍵生成ミスによるものです。発覚から主要ブラウザの遮断までは数時間という異例の速さでした。まずは事案の全体像と、影響を受けた証明書を整理します。

### 何が起きたのか

2026年10月17日（協定世界時）、[eMudhra](https://emudhra.com/)が発行した中間CA証明書8枚について、秘密鍵が漏えいしているとの報告が寄せられました。eMudhraはインドの電子署名・PKI事業者で、emSignブランドでSSL/TLS証明書を発行しています。

報告者のWayne氏は、8枚すべての秘密鍵で同じメッセージに電子署名し、鍵を実際に持っていることを証明しました。報告は[Mozilla](https://www.mozilla.org/)、Google、Apple、Microsoftの各ルートプログラムとeMudhraに送られています。

### 影響を受けた中間CA証明書

影響を受けたのは、2025年4月30日に作成された楕円曲線暗号（P-384）の中間CA証明書8枚です。欧州拠点向けのG3B系（eMudhra BV）と、米国拠点向けのG3C系（eMudhra Inc）に分かれています。いずれも同じ日の鍵生成作業で作られたもので、用途別の内訳と上位のルート証明書は次のとおりです。

| 用途 | 中間CA証明書 | 上位のルート証明書 |
| --- | --- | --- |
| TLS（DV） | EM DV TLS CA - G3B／G3C | emSign Root TLS CA - G3 |
| TLS（OV） | EM OV TLS CA - G3B／G3C | emSign Root TLS CA - G3 |
| TLS（EV） | EM EV TLS CA - G3B／G3C | emSign Root TLS CA - G3 |
| コード署名 | EM OV CS CA - G3B／G3C | emSign Root CS CA - G3 |

TLS用の6枚は、Chrome、Firefox、Safari、Edgeが信頼するルートにつながっていました。コード署名用の2枚はMicrosoftが信頼しています。さらに8枚とも[Sectigo](https://www.sectigo.com/)のルートからもクロス署名を受けていたため、eMudhraのルートを信頼しない環境にも影響範囲が広がりました。

## 秘密鍵漏えいによる被害と背景

中間CAの秘密鍵が第三者の手に渡ると、インターネットを支える証明書の信頼の仕組みそのものが揺らぎます。ここでは、秘密鍵の漏えいで想定される被害と、現時点で分かっている実際の悪用の有無について確認します。

### なぜなりすましが可能になるのか

Webサイトの鍵マークは、認証局がそのサイトの身元を保証していることを示します。中間CAの秘密鍵があれば、攻撃者は銀行や官公庁を含む任意のドメインについて、ブラウザが正規と判断する証明書を作れてしまいます。

通信経路に割り込める攻撃者がこの証明書を使えば、本物のサイトになりすまし、通信内容を盗み見たり書き換えたりできます。

### 実際の悪用は確認されているのか

eMudhraによると、8枚のうち実際に運用していたのはEM DV TLS CA - G3Cの1枚だけで、利用者向けの証明書は発行していないとしています。

また、証明書の発行を記録するCT（Certificate Transparency）ログには、該当期間の記録がありませんでした。CTを必須とする主要ブラウザは攻撃されていなかったとみられます。ただし、CTを確認しないアプリや機器が狙われたかどうかは分かっていません。

## 技術的な詳細：秘密鍵が256通りしかなかった

今回の原因は、高度な攻撃ではなく、鍵を作る段階での単純な誤りでした。Mozillaが公開したインシデント報告とeMudhraの説明をもとに、秘密鍵が復元可能になった仕組みと、見逃されていた予兆を整理します。

### 秘密鍵が極端に小さい整数だった

P-384の秘密鍵は、本来は約384ビットの巨大な乱数から選ばれます。ところがMozillaの調査では、影響を受けた8枚の秘密鍵はいずれも256未満の整数でした。

つまり鍵は最後の1バイト以外がすべてゼロという状態で、公開されている証明書から一瞬で逆算できます。Mozillaは報告者の手法を知らないまま、報告の約1時間40分後に独自に鍵を復元しています。

### 鍵生成手順のミスが原因

eMudhraの説明によると、この日の鍵生成作業では、鍵を海外拠点へ持ち出すためのテストとして、通常と異なる手順が承認されていました。その際、スクリプトの不具合で弱い鍵がもう1組作られました。

さらにラベル名が似ていたため、本来の鍵ではなく弱い鍵で証明書署名要求を作成し、ルートの署名とクロス署名を受けていたとしています。

### 見逃されていた予兆

同じ6枚のTLS用中間CAをめぐっては、2025年5月にも、失効リスト（CRL）の署名が無効という不具合が報告されていました。

eMudhraは今回、当時は本来の鍵で署名した結果エラーになったため、弱い鍵で署名し直していたと説明しています。鍵の取り違えに気づく機会がありながら、1年以上見過ごされていたことになります。

## eMudhra・ブラウザ各社の対応

報告を受けたブラウザ各社と認証局、クロス署名元のSectigoは、週末にもかかわらず短時間で対応を進めました。ここでは、中間CA証明書のブロックと失効の時系列、そしてルート証明書の扱いの変化を順に見ていきます。

### ブラウザ・OSによるブロック

各社は、失効情報を配信する独自の仕組みを使って、該当する中間CA証明書を遮断しました。FirefoxのOneCRLやChromeのCRLSetsは、ブラウザの更新や再起動なしで保護を届けられるのが特徴です。報告から各社の遮断、失効までの主な対応の流れを時系列で整理すると次のとおりです（日時は協定世界時）。

| 日時 | 対応 |
| --- | --- |
| 10月17日 20:06 | Mozillaが報告を受領 |
| 10月17日 22:59 | FirefoxがOneCRLで遮断を完了。Chromeも同日に遮断 |
| 10月18日 09:24〜09:38 | eMudhraが8枚を失効（理由：CA侵害） |
| 10月19日 | Appleが遮断。Sectigoがクロス署名を失効 |
| 10月20日 | Microsoftが遮断。Firefox 158.0.1、NSS 3.131.1を公開 |

Firefoxは、OneCRLを受け取れない設定の利用者向けに、Firefox 158.0.1とESR 115.43.1、153.5.1も公開しました。Mozillaの証明書リスト（NSS）を使う他のアプリ向けには、NSS 3.131.1で上位のルート証明書を削除しています。報告から4日で、主要な配布経路の対応がほぼそろいました。

### ルート証明書の信頼取り消しへ

その後、複数の人物が独自に秘密鍵を復元し、一部はインターネット上で公開したことが判明しました。これを受けてMozillaは、上位のemSign ECC Root CA - G3の信頼を緊急で取り消すと決定し、Googleも同様の方針を示しています。

eMudhraはこのルート配下での発行を停止しました。移行が必要な証明書は約3万枚で、その約97%はACMEによる自動発行です。

### Cloudflareや開発言語の対応

[Cloudflare](https://www.cloudflare.com/)は10月19日に問題を把握し、WARPアプリやCloudflare Tunnel（cloudflared）のセキュリティ更新を公開しました。

開発言語でも、Goが1.27.3と1.26.10（CVE-2026-111943）を、Node.jsが22.23.4などを公開しています。Pythonのcertifiや主要Linuxのca-certificatesも順次更新されています。

## 利用者への注意点

一般の利用者と、開発者・サーバー管理者とでは、必要な対応が大きく異なります。ブラウザは自動で守られている一方、それ以外のプログラムは更新しない限り危険な中間CAを信頼し続けます。立場別に確認すべきポイントを整理します。

### 一般利用者はブラウザとOSを最新に

主要ブラウザはすでに該当証明書をブロックしているため、一般の利用者が過度に心配する必要はありません。ただし、更新を止めている端末には保護が届いていない可能性があります。

ブラウザとOSを最新版に更新してください。更新が止まった古いスマートフォンやネットワーク機器は、特に注意が必要です。

### 開発者・サーバー管理者は証明書ストアの更新を

サーバー上のスクリプトや業務アプリなど、ブラウザ以外のプログラムの多くは失効情報を確認せず、独自に持つ証明書ストアだけで接続先を判断します。そのため、ブラウザ側でブロックされていても、プログラム側の証明書ストアを更新しない限り危険な中間CAを信頼し続けます。主な更新対象と修正版のバージョンは次のとおりです。

- Ubuntu、Debian、Fedora、Alpineなどのca-certificatesパッケージ
- Python certifi 2026.10.19、pip 26.2.2
- Go 1.27.3／1.26.10
- Node.js 22.23.4／24.22.1／26.12.1
- curlのCAバンドル（2026-10-20版）
- Electron 44.9.1／43.8.1／42.11.16

コンテナイメージに証明書ストアを同梱している場合は、ベースイメージを更新したうえで、イメージの再ビルドとデプロイが必要です。また、macOS標準のcurlやgit、python3は更新された失効情報を参照しません。告知サイトで案内されている、ルート証明書を取り除く回避策の適用もあわせて検討してください。

### 対処済みかを確認する方法

告知サイト（[emudhra.we-have-a-problem.com](https://emudhra.we-have-a-problem.com/)）には、影響を受けた中間CAの証明書を使うテスト用サーバーが用意されています。

コマンドラインで `curl https://dv-g3b-emudhra.we-have-a-problem.com/` を実行し、証明書エラーになれば対処済みです。正常に表示される場合、その環境はまだ危険な中間CAを信頼しています。

## 企業が取るべき対策

今回の件は、自社で契約していない認証局のミスでも、自社のシステムが影響を受けることを示しました。認証局のミスは利用者側では防げないため、同様の事案はいつ起きてもおかしくありません。平時から備えておくべき対策を紹介します。

### 証明書ストアの棚卸し

企業内には、OSやブラウザ以外にも、Javaのキーストア、業務アプリ、プロキシ、ネットワーク機器など、独自の証明書ストアを持つ仕組みが数多くあります。

どのシステムがどの証明書ストアを使い、誰が更新するのかを一覧にしておきましょう。緊急時に、影響範囲の確認と更新を素早く進められます。

### 証明書の自動更新（ACME）を整える

eMudhraの移行対象の約97%がACMEによる自動発行だったことは、移行の負担を大きく下げる要素です。証明書の発行と更新を自動化していれば、認証局の乗り換えも設定変更で済みます。

手作業で更新している証明書が多い組織は、自動化の対象を広げておくことが有効です。

### emSign証明書の利用者は早めに移行を

自社サイトでemSignの楕円曲線（ECC）証明書を使っている場合は、ブラウザでエラーになる前に別のチェーンや別の認証局へ切り替える必要があります。

eMudhraはRSA方式のemSign Root CA - G1配下への移行を進めるとしています。案内を確認し、証明書の再発行と差し替えを進めてください。

## 秘密鍵漏えい事案から得られる業界への教訓

今回の事案は、認証局の鍵管理、証明書の透明性（CT）、AIによる解析能力の進化という3つの観点で、多くの教訓を残しました。認証局だけでなく、証明書を利用して通信するすべての企業や組織に関わる内容です。

### 鍵の品質を確かめる仕組みの必要性

今回の秘密鍵は専用の暗号装置（HSM）で作られ、ルートの署名とクロス署名の手続きも通過していました。それでも、鍵そのものが極端に弱いことには1年半近く誰も気づきませんでした。

鍵の取り違えを防ぐ二重確認や、生成した鍵の強度を機械的に検証する手順の重要性が浮き彫りになっています。

### CTの効果と限界

CTを必須とするブラウザでは、ログに記録のない証明書は受け入れられません。今回、主要ブラウザの利用者が守られたのは、この仕組みによるところが大きいといえます。

一方で、CTを確認しないアプリや機器では同じ防御が働きません。ブラウザ以外の通信で失効情報やCTをどう活用するかが、今後の課題です。

### AIで誰でも解ける時代の暗号ミス

MozillaはAIエージェントに簡単な指示を与えただけで、初回で秘密鍵を復元できたと報告しています。暗号の専門知識がない人でも、鍵の欠陥を突ける時代になりました。

報告者は公開された証明書データを機械的に調べて欠陥を見つけましたが、攻撃者も同じ方法をとれます。設定や実装のミスが見つかるまでの時間は、今後さらに短くなると考えるべきです。

## まとめ

eMudhraの中間CA証明書8枚は、鍵生成時のミスにより、公開情報から誰でも秘密鍵を復元できる状態でした。主要ブラウザとOSは発覚から数日以内に遮断を終え、CTの仕組みによってブラウザ利用者への攻撃は防がれたとみられます。さらに鍵の公開を受けて、上位のルート証明書の信頼取り消しにまで発展しました。

一方、CTや失効情報を確認しないアプリや機器では、ソフトウェアの更新が欠かせません。一般の利用者はブラウザとOSを最新に保ち、開発者や企業は証明書ストアの更新と棚卸し、証明書の自動更新の整備を進めましょう。
