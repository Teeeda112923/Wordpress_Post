# APIとは？仕組み・種類・具体例と、なぜ今サイバー攻撃で狙われるのかをわかりやすく解説

APIとは、異なるソフトウェアやサービスが互いの機能やデータを利用するための接続口のことです。
スマホアプリやネット決済、地図の表示など、私たちが毎日使うサービスの多くを裏側で支えている、現代のITに欠かせない技術です。

一方で2026年9月前後には、APIを経由した不正操作などによる個人情報の漏えいが国内で相次ぎ、JPCERT/CCが注意喚起を公表しました。
本記事では、APIの意味や仕組み、種類、具体例といった基本から、攻撃者に狙われる理由と企業が取るべき対策までを、IT初心者にもわかるよう順を追ってわかりやすく解説します。

## APIとは？意味をひと言でいうと

APIはApplication Programming Interfaceの略で、日本語ではアプリケーション・プログラミング・インターフェースと呼ばれます。
ひと言でいえば、あるソフトウェアの機能やデータを、別のソフトウェアから決められたルールで呼び出すための接続口です。

よく使われるたとえが、レストランの注文係です。
客にあたる利用側のアプリは、厨房にあたる提供側のシステムへ直接入らず、注文係であるAPIにメニューどおり注文するだけで、料理にあたるデータや処理結果を受け取れます。
厨房の中身を知らなくても機能を使える点が、APIの最大の特徴です。

## APIの仕組み

APIのやり取りは、利用する側が依頼を送り、提供する側が結果を返すというシンプルな流れで成り立っています。
ここでは基本の流れと、セキュリティを考えるうえで欠かせない用語を、具体的なイメージとともに押さえておきましょう。

### リクエストとレスポンスでやり取りする

APIを使う側のプログラムは、決められた形式で「この情報がほしい」「この処理をしてほしい」という依頼を送ります。
この依頼をリクエスト、提供側から返ってくる結果をレスポンスと呼びます。

現在のWebサービスでは、インターネットの標準的な通信方式であるHTTPSでリクエストを送り、JSONという形式のデータで結果を受け取る方法が主流です。
人が画面を操作しなくてもプログラム同士で自動的に通信できるため、処理の効率化や大量のデータ連携が可能になります。

### APIを理解するための基本用語

APIの仕組みやセキュリティに関する記事を読むと、エンドポイントやAPIキー、トークンといった専門用語が頻繁に登場します。
これらは攻撃の手口を説明するときにも必ず使われる言葉で、意味を知っておくと注意喚起やニュースの内容がぐっと理解しやすくなるはずです。
代表的な用語とその意味を、次の表にまとめました。

| 用語 | 意味 |
|---|---|
| エンドポイント | APIを呼び出すための接続先のURL。機能ごとに用意される |
| リクエスト／レスポンス | 利用側が送る依頼と、提供側が返す結果 |
| APIキー | APIの利用者を識別するための文字列。合鍵のような役割を持つ |
| アクセストークン | ログイン後などに発行される、一定期間有効な通行証 |
| 認証／認可 | 認証は相手が誰かの確認、認可はその相手に何を許すかの判断 |

なかでもセキュリティ上特に重要なのが、APIキーやアクセストークンの扱いと、認可の設計です。
キーやトークンが第三者に知られたり、認可の確認が甘かったりすると、正規の利用者になりすまして情報を引き出されたり、データを書き換えられたりするおそれがあります。
後半で紹介する国内の攻撃事例も、まさにこの部分の弱点を突いたものです。

## APIの主な種類

APIは、誰に公開しているかという公開範囲と、どのような方式で通信するかという技術的な違いで分類できます。
両方の視点を知っておくと、自社が提供・利用しているAPIのうち、どれを優先して守るべきかを整理しやすくなります。

### 公開範囲による分類

APIは、外部の誰でも使えるものから、社内のシステム同士だけで使うものまで、公開範囲によって性格や求められる対策が大きく異なります。
注意したいのは、外部に公開していないつもりの内部APIでも、スマホアプリの通信先などから存在を知られてしまう場合があるという点です。
公開範囲による主な分類は、次の3つです。

- オープンAPI（パブリックAPI）：外部の開発者に広く公開され、登録すれば誰でも利用できる
- パートナーAPI：契約を結んだ取引先や提携企業など、限られた相手だけに提供される
- 内部API（プライベートAPI）：自社のアプリとサーバー、社内システム同士の連携など、自社内で使われる

内部APIは、利用者が自社のアプリや社員に限られている前提で作られるため、認証やアクセス制御が手薄になりがちです。
しかし攻撃者から見れば、内部向けかどうかは関係なく、接続先やキーさえわかれば攻撃を試みる対象になります。
公開範囲にかかわらず、すべてのAPIを守るべき入り口とみなして設計・運用することが大切です。

### 通信方式による分類

APIには、データの受け渡し方のルールが異なるいくつかの方式があり、開発するサービスの性質や求められる性能によって使い分けられます。
現在のWebサービスではREST APIが最も広く使われていますが、用途に応じて別の方式が選ばれることもあり、それぞれに得意な分野があります。
代表的な4つの方式を、次の表で比較します。

| 方式 | 特徴 |
|---|---|
| REST API | URLとHTTPの命令を組み合わせて操作する。シンプルで最も普及している |
| GraphQL | 必要なデータの項目を利用側が指定して、まとめて取得できる |
| SOAP | 厳密な規格に沿ってXML形式でやり取りする。金融や基幹システムで使われてきた |
| gRPC | 高速な通信が得意で、システム内部のサービス同士の連携で使われる |

どの方式を採用しても、APIが重要な機能やデータへの入り口である点は変わりません。
方式ごとに設定や実装の注意点は異なりますが、誰からのアクセスを受け付け、どの操作を許可するかを明確にするという基本は共通しています。
技術を選ぶときは、機能や性能だけでなく、安全な守り方まで同時に考えておくことが重要です。

## 身近なAPIの具体例

APIは専門家だけが扱うものではなく、一般の利用者が意識しないまま毎日のように使っている技術です。
身近な例を知ると、APIが果たしている役割と、そこが攻撃者に狙われたときの影響の大きさがイメージしやすくなります。

### 日常のサービスに組み込まれたAPI

飲食店のWebサイトに地図が表示されたり、SNSのアカウントで別のサービスにログインできたりするのは、裏側でAPIを使って外部の機能を呼び出しているからです。
自社でゼロから開発しなくても、他社が提供する高度な機能を手軽に組み込めるのが、APIの大きな強みといえます。
代表的な利用例を、次にまとめました。

- Webサイトに表示される地図や天気予報
- SNSやGoogleのアカウントを使ったログイン連携
- ネットショップのクレジットカード決済やコード決済
- 宿泊予約サイトでの空室や料金の一括比較
- 生成AIの機能を自社のアプリや業務システムに組み込む連携

これらのサービスでは、利用者の氏名や住所、決済情報、ログイン情報といった重要なデータが、APIを通じて日々やり取りされています。
つまりAPIは便利さの源であると同時に、守るべき大切な個人情報の通り道でもあります。
そのため、APIを提供する側の企業は、その責任を常に強く意識して管理しなければなりません。

### スマホアプリの裏側もAPIでできている

スマホアプリの多くは、画面に表示する情報をその都度サーバーから取得しており、その通信にもAPIが使われています。
会員情報の表示やポイントの確認、予約の変更といった操作は、裏側ではすべてAPIへのリクエストです。

アプリは誰でもダウンロードできるため、攻撃者がアプリを解析して通信先やキーを調べることも技術的には可能です。
後述する2026年9月前後の国内事案でも、この点が悪用されたと報告されています。

## APIを使うメリット

企業がAPIを活用する最大のメリットは、開発の手間とコストを抑えながら、高品質なサービスをスピーディーに提供できることです。
他社が提供する決済や地図、認証の仕組みを利用すれば、自社は本来注力すべきサービス開発に集中でき、社内外のデータ連携による業務の自動化も進められます。
主なメリットは、次の4つです。

- 開発期間とコストを削減できる
- 専門企業が提供する高品質な機能や最新のデータを利用できる
- 社内外のシステムを連携させ、業務を自動化できる
- 自社のデータや機能を公開し、新たなビジネスを生み出せる

一方で、APIを増やせば増やすほど、外部から到達できる入り口も増えていきます。
どのAPIがどこに公開され、誰がどのように使っているのかを把握できていない状態は、攻撃者にとって格好の標的となります。
APIのメリットを十分に享受するためには、利用の拡大とセットで、管理と防御の体制を整えておく必要があります。

## なぜAPIはサイバー攻撃で狙われるのか

APIが狙われるのは、重要なデータや機能に直接つながる入り口でありながら、画面の操作とは違って人の目が届きにくいからです。
ここでは主な理由を2つ挙げたうえで、2026年9月前後に国内で実際に起きた事案を紹介します。

### データと機能に直結しているから

APIの先には、顧客情報や会員データ、決済などの重要な機能がつながっています。
Webサイトの画面は見た目を整えるための部分にすぎず、実際のデータはAPIを通じて出し入れされているのが一般的です。

そのため攻撃者は、画面を経由せずにAPIへ直接リクエストを送り、データを取得しようとします。
プログラムで自動化すれば、短時間に大量の情報を引き出すことも可能です。

### 画面にない機能も呼び出せてしまうから

アプリの画面では表示されない管理用の機能も、裏側ではAPIとして用意されていることがあります。
画面上にボタンがないから安全だと考え、API側で権限の確認をしていないと、攻撃者に直接呼び出されてしまいます。

たとえば一般の会員が、本来は管理者しか使えないAPIを呼び出して自分の権限を書き換える、といった攻撃が考えられます。
画面とAPIのどちらで制御しているのかを曖昧にしたまま運用することが、大きなリスクにつながります。

### 2026年9月前後に国内で相次いだAPI経由の不正アクセス

<a href="https://www.jpcert.or.jp/" target="_blank" rel="noopener">JPCERTコーディネーションセンター（JPCERT/CC）</a>は2026年10月8日、国内組織で不正アクセスによる個人情報などの漏えいが相次いでいるとして注意喚起を公表しました。
そのなかで、特に増加しているおそれのある攻撃類型の一つとして、API経由での不正な操作を挙げています。
報告されている主な手口は次のとおりです。

- 一般公開されているスマホアプリを解析し、APIの接続先やキーを特定する
- 画面操作では実行できない内部APIを攻撃し、ユーザー権限の変更や不正なアカウントの作成を行う
- 不正な形式の認証情報を送るなどして応答の違いを確かめ、アカウント情報を探る
- 別のシステムへの侵害で盗んだAPIキーを使ってアクセスする

同じ注意喚起では、BIツールのMetabaseにあるSQLインジェクションの脆弱性（CVE-2026-72898）も、APIへの不正なリクエストを通じて悪用されると説明されています。
被害は一般向けアプリだけでなく、従業員向けの管理システムなど外部からのアクセスを想定していないシステムにも及んでいます。
APIの安全性は、もはや一部の開発者だけの課題ではありません。

## APIの代表的なセキュリティリスク

APIの弱点には典型的なパターンがあり、国際的なセキュリティコミュニティであるOWASPがその傾向をまとめて公開しています。
代表的なリスクをあらかじめ知っておくことは、自社のAPIを点検する際の大切な出発点になります。

### OWASP API Security Top 10とは

<a href="https://owasp.org/" target="_blank" rel="noopener">OWASP（Open Worldwide Application Security Project）</a>は、Webアプリケーションのセキュリティ向上に取り組む国際的なコミュニティです。
OWASPはAPI特有の重大なリスクをOWASP API Security Top 10として公開しており、2023年版が最新の改訂版となっています。
JPCERT/CCも、API対策の参考としてこのガイドラインを挙げています。

| 番号 | リスク名（日本語訳） |
|---|---|
| API1 | オブジェクトレベルの認可の不備（BOLA） |
| API2 | 認証の不備 |
| API3 | オブジェクトプロパティレベルの認可の不備 |
| API4 | 制限のないリソース消費 |
| API5 | 機能レベルの認可の不備 |
| API6 | 重要なビジネスフローへの制限のないアクセス |
| API7 | サーバーサイドリクエストフォージェリ（SSRF） |
| API8 | セキュリティの設定ミス |
| API9 | 不適切な資産管理（APIの棚卸し不足） |
| API10 | APIの安全でない利用 |

上位に並ぶリスクの多くは、高度なハッキング技術を必要とするものではなく、認証や認可の確認漏れといった設計・運用上の不備に起因しています。
裏を返せば、認証と認可の確認という基本的な対策を一つずつ徹底するだけで防げる攻撃も少なくありません。
次の項目では、なかでも特に被害につながりやすいリスクを詳しく見ていきます。

### 特に注意したい3つのリスク

OWASP API Security Top 10に挙げられたリスクのうち、情報漏えいや不正操作に特に直結しやすいのが、認可と認証に関するリスクです。
いずれも、APIがリクエストを受け取ったときに、相手が誰で、その操作を許してよいかを正しく確認していないことが主な原因です。
代表的な3つのリスクと、その具体例は次のとおりです。

- オブジェクトレベルの認可の不備：URLやリクエスト内の番号を書き換えるだけで、他人の会員情報などを閲覧できてしまう
- 認証の不備：推測しやすいトークンや有効期限の長いキー、総当たり攻撃への対策不足などにより、なりすましを許してしまう
- 機能レベルの認可の不備：一般の利用者が、管理者向けのAPIを呼び出して権限変更などの操作を実行できてしまう

2026年9月前後の国内事案で報告された、内部APIを使った権限変更や不正なアカウント作成は、機能レベルの認可の不備にあたる典型的な手口といえます。
画面で制限しているから大丈夫という思い込みを捨て、API側で毎回確認する設計にすることが欠かせません。
自社のAPIが同じ弱点を抱えていないか、早めに点検しましょう。

## 企業が取るべきAPIセキュリティ対策

APIの対策は、アクセスの制御、利用量の制限、認証情報の管理、そしてAPI全体の把握という4つの視点で考えると整理しやすくなります。
JPCERT/CCが示した推奨対策を軸に、取り組むべきポイントを紹介します。

### JPCERT/CCが推奨するAPI経由のアクセスへの対策

JPCERT/CCは2026年10月の注意喚起のなかで、報告された実際の攻撃手口に基づき、API経由のアクセスに対する具体的な対策を示しています。
どれも特別な製品を導入しなくても着手できるものが中心で、自社のAPIを点検する際のチェックリストとしてそのまま活用できます。
主な推奨対策は、次の6つです。

- 単位時間あたりのリクエスト件数を制限し、短時間の繰り返しアクセスや大量実行を防ぐ
- ログインやパスワードリセット、SMS送信、検索など悪用されやすい機能には個別に回数制限を設ける
- 非公開のものを含むすべてのエンドポイントでアクセス制御を行い、許可した利用者と操作だけを受け付ける
- 利用者やAPIトークンには必要最小限の権限だけを与える
- トークンに適切な有効期限を設定し、長期間有効なものを使わない
- 不要になったトークンや漏えいが疑われるトークンを速やかに無効化できるようにしておく

あわせて、利用地域が限られるサービスではアクセス元の地域を制限することや、既知の脆弱性への修正アップデートを適用することも推奨されています。
業務に不要な管理機能がインターネットに公開されていれば停止し、保存期間を過ぎたデータを残さないことも、被害を小さくするうえで有効です。
できるところから順に対応を進めましょう。

### APIの棚卸しで守る範囲を明確にする

どれだけ対策を用意しても、守るべきAPIを把握していなければ抜け漏れが生じます。
開発の過程で作られたまま放置された古いAPIや、テスト用に一時的に公開したAPIが、攻撃の入り口になる例は少なくありません。

まずは自社のAPIを一覧化し、公開範囲や利用者、扱うデータ、担当部署を整理しましょう。
OWASP API Security Top 10でも、不適切な資産管理が独立したリスクとして挙げられています。

### 社内向けシステムやアプリのキー管理も見直す

JPCERT/CCの注意喚起では、BIツールや従業員向けの管理システムなど、不特定多数の利用を想定していないシステムでも被害が確認されています。
社内向けだから安全とは考えず、外部から到達できる状態になっていないかを確認することが重要です。

また、スマホアプリに認証用のキーを埋め込むと、アプリの解析によって取り出されるおそれがあります。
アプリ内のキーは知られる前提で設計し、利用者ごとのトークンとサーバー側の認可で守る仕組みにしましょう。

## 利用者が気をつけたいこと

APIの安全性を確保するのは基本的にサービスを提供する企業の責任ですが、利用者自身も被害を小さくするための備えができます。
漏えいした情報が別のサービスへの不正ログインなどに悪用される二次被害を防ぐことが、利用者にとって最も重要なポイントになります。
日頃から意識しておきたい主な対策は、次のとおりです。

- サービスごとに異なるパスワードを設定し、使い回さない
- 多要素認証が使えるサービスでは必ず有効にする
- SNSや外部サービスとの連携設定を定期的に見直し、使っていない連携を解除する
- 漏えいを公表した企業からのお知らせを確認し、パスワード変更など案内された対応を行う
- 漏えいに便乗したフィッシングメールやSMSのリンクを安易に開かない

特にパスワードの使い回しは、一つのサービスで情報が漏れただけで、ほかのサービスのアカウントまで連鎖的に乗っ取られる原因になります。
多要素認証を有効にしておけば、万一パスワードが知られても、不正ログインを防げる可能性が高まります。
自分の大切な情報を守るために、今日からできることを一つずつ始めましょう。

## まとめ

APIとは、ソフトウェアやサービス同士が機能やデータをやり取りするための接続口であり、地図表示やログイン連携、決済、スマホアプリなど、身近なサービスの多くを支えています。
便利な技術である一方、重要なデータや機能に直結しているため、攻撃者にとって魅力的な標的でもあります。

2026年9月前後に国内で相次いだ不正アクセスでも、アプリの解析によるキーの特定や内部APIの悪用が報告されました。
企業はアクセス制御や回数制限、トークン管理、APIの棚卸しを徹底し、利用者はパスワードの使い回しをやめて多要素認証を有効にすることが大切です。
